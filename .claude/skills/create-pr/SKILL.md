# Pull Request 作成スキル

このスキルは現在のブランチの変更内容を分析し、GitHubにPull Requestを作成します。
変更内容に応じて、Mermaid記法のクラス図・シーケンス図をPR本文に含めます（GitHubがネイティブレンダリング）。

## 実行手順

### 0. 引数の解析

スキルの引数を解析する:

- **`--draft`** フラグが含まれている場合、ドラフトPRとして作成する

### 1. 変更内容の収集と分析

**Agent ツール（`subagent_type: general-purpose`）で以下のsubagentを起動する:**

```
subagent_type: general-purpose
prompt: |
  このブランチの変更情報を収集・分析してください。

  ## Step 1: Git情報の収集
  以下のgitコマンドを実行:
  1. git fetch origin main
  2. git status
  3. git diff --name-status origin/main...HEAD
  4. git log origin/main..HEAD --oneline --no-merges
  5. git diff origin/main...HEAD --stat
  6. git diff origin/main...HEAD（実際の差分内容）

  ## Step 2: 変更内容の分析
  収集した差分をもとに以下を分析:
  - 変更されたファイルの役割と機能
  - 変更の目的（新機能追加、バグ修正、リファクタリング、UI変更など）
  - 影響を受けるコンポーネントや機能
  - 破壊的変更があるか

  ## Step 3: コード構造と呼び出しフローの収集
  変更されたファイルに含まれる主要な構造（コンポーネント・クラス・型・フック・関数など、
  プロジェクトの言語/フレームワークに応じたもの）について:
  - 追加・変更された構造の定義（Props/引数、State/フィールド、メソッド）
  - 各構造が「新規追加」か「既存の変更」かを明記すること
  - 構造間の関係（親子関係、依存関係、データの受け渡し）

  変更に含まれる処理フローについて:
  - 処理の起点（ユーザー操作、APIリクエスト、イベント、バッチ起動など）
  - 呼び出しチェーン（起点 → ハンドラ/関数 → 状態更新/副作用）
  - 主要な条件分岐やエラーハンドリングフロー

  ## Step 4: CI/ワークフロー構造の収集（CI設定ファイルが変更されている場合のみ）
  `.github/workflows/` 配下のファイルが変更されている場合:
  - 変更前（main側）のジョブ一覧とジョブ間の依存関係（`needs`）を読み取る
  - 変更後（HEAD側）のジョブ一覧とジョブ間の依存関係を読み取る
  - ジョブの追加・削除・リネーム・依存関係の変更を特定する

  重要: 変更ファイルだけでなく、参照先の関連ファイルも Read ツールで読み、
  正確な関係性を把握すること。特に以下を確認:
  - 変更された構造の呼び出し元（親コンポーネント・呼び出し側の関数）
  - 受け渡されるハンドラやデータの型定義
  - 呼び出し先のコンポーネントやユーティリティの定義

  ## 報告フォーマット
  以下の構造で報告:
  - 変更ファイル一覧（name-status）
  - コミット一覧
  - 差分の統計（stat）
  - 変更の目的と概要（日本語）
  - 影響範囲
  - 破壊的変更の有無
  - **コード構造情報**: 追加・変更された構造の一覧（新規/変更の区別を明記）、Props/引数、State、関係性の一覧
  - **呼び出しフロー情報**: 起点、呼び出しチェーン、主要な分岐の一覧
  - **ワークフロー構造情報**（CI設定変更時のみ）: 変更前後のジョブ一覧と依存関係
```

### 2. 分析結果の統合

subagentの結果を受け取ったら、以下を判断する:

- **変更の目的**: コミットメッセージと差分から、このPRが何を達成しようとしているか
- **変更の種類**: 機能開発、仕様変更、バグ修正、リファクタリング、その他のいずれか
- **影響範囲**: どのコンポーネント・機能に影響があるか
- **破壊的変更の有無**: 既存機能への影響、設定ファイルの変更などがあるか

### 3. Mermaid 図表の生成

subagentから受け取ったコード構造情報と呼び出しフロー情報をもとに、Mermaid記法で図表を生成する。

#### 図表を生成する条件

以下のいずれかに該当する場合に図表を生成する:
- コンポーネント・クラス・インターフェースの追加・変更がある → **クラス図**を生成
- 複数の構造間の呼び出しフローが変更されている → **シーケンス図**を生成
- CI/CDワークフローファイル（`.github/workflows/`）の変更がある → **ワークフロー図（Before/After）**を生成

以下の場合は図表を**スキップ**し、セクション自体を省略する:
- ドキュメントのみの変更
- CI/CD以外の設定ファイルのみの変更（`.gitignore`, `.prettierrc` 等）
- 単一ファイル内の軽微な修正（typo修正、定数値変更など）
- コメントアウトのみの変更

#### クラス図

変更に関連するコンポーネント・型の構造と関係性を示す図。
レビュアーが「何が追加・変更され、既存コードとどう繋がるか」を一目で把握できることが目的。

**スコープ**:
- 変更されたコンポーネント/型を中心に据える
- その直接の関連（呼び出し元、引数/Props型、依存するユーティリティ）を含める
- 変更と無関係な構造は含めない

**新規/変更の区別**:
レビュアーが「どれが今回のPRで追加・変更されたものか」を一目で識別できるよう、ステレオタイプ + 色分けで区別する:
- 新規追加 → `<<new>>` ステレオタイプ + 緑系の背景色（`style ClassName fill:#d4edda,stroke:#28a745,color:#155724`）
- 既存の変更 → `<<modified>>` ステレオタイプ + 黄系の背景色（`style ClassName fill:#fff3cd,stroke:#ffc107,color:#856404`）
- コンテキスト用の既存構造 → ステレオタイプなし、スタイルなし（デフォルト色）

**記法**:
- Props・Stateは変更の理解に必要なものだけ記載（全項目の列挙は不要）
- 関係: `<|--` 継承、`<|..` 実装、`-->` 依存（props渡し等）、`..>` 間接依存
- `style` ディレクティブはクラス定義・関係の後にまとめて記述する

**例**:
```
classDiagram
    class LayoutMenu {
        <<modified>>
        +props: LayoutMenuProps
        +handleSelectLayoutSet()
        +handleSubmit()
    }
    class LayoutItem {
        +props: LayoutItemProps
        +handleSelect()
    }
    class FloorPlanModelListModal {
        <<new>>
        +isOpen: boolean
        +handleSelectFloorPlan()
    }
    LayoutMenu --> LayoutItem : renders
    LayoutMenu --> FloorPlanModelListModal : renders

    style LayoutMenu fill:#fff3cd,stroke:#ffc107,color:#856404
    style FloorPlanModelListModal fill:#d4edda,stroke:#28a745,color:#155724
```

#### シーケンス図

変更部分を通るユーザー操作/処理の流れを示す図。
レビュアーが「この変更で処理がどう流れるか」を追えることが目的。

**スコープ**:
- 変更によって新規追加または修正された処理フローを示す
- 既存の未変更フローは含めない

**記法**:
- participant は実際のコンポーネント名・モジュール名を使う
- イベントハンドラ・関数は実際の名前を使う
- 条件分岐 `alt`/`else`、ループ `loop`、オプション `opt` を適宜使う

**例**:
```
sequenceDiagram
    participant User
    participant LeftMenuDrawer
    participant Main
    participant LayoutMenu

    User->>LeftMenuDrawer: 間取り作成ボタンクリック
    LeftMenuDrawer->>Main: handleLayoutMenu()
    Main->>LayoutMenu: open
    User->>LayoutMenu: FLOOR PLAN連携を選択
    LayoutMenu->>LayoutMenu: handleSelectCapturedStructure()
    LayoutMenu->>Main: onSubmit(selectedLayout)
```

#### ワークフロー図（CI/CD変更時）

`.github/workflows/` 配下のファイルが変更された場合に、ジョブ依存関係の変更前後を示す図。
レビュアーが「CIパイプラインの構造がどう変わるか」を一目で把握できることが目的。

**構成**: Before（変更前）と After（変更後）の2つの flowchart を並べる。

**記法**:
- `flowchart LR`（左→右）でジョブの依存関係を表現
- ノードはジョブ名をそのまま使う
- 矢印（`-->`）は `needs` による依存関係を示す
- Before図: 削除/リネームされるジョブを赤系でハイライト（`style nodeName fill:#f8d7da,stroke:#dc3545,color:#721c24`）
- After図: 追加/リネーム後のジョブを緑系でハイライト（`style nodeName fill:#d4edda,stroke:#28a745,color:#155724`）
- 変更されないジョブはデフォルト色のまま

#### サイズの上限

図表が大きくなりすぎるとかえって読みにくくなるため、以下を目安に核心部分に絞る:
- クラス図: 10クラス以内
- シーケンス図: 15ステップ以内
- ワークフロー図: 各15ジョブ以内

### 4. PR本文の作成

以下のテンプレートに沿ってPR本文を作成してください:

```markdown
## 修正内容

### 概要
[日本語での変更概要を1-3文で記述]

### 変更点
- [具体的な変更点1]
- [具体的な変更点2]
- ...

### 設計図 / Diagrams

> このセクションは図表（アーキテクチャ図・クラス図・シーケンス図・ワークフロー図）を生成・更新した場合のみ含める。
> 図表が無い場合はこのセクション自体を省略する。

## セルフレビュー

- [ ] 差分確認
- [ ] タイポチェック
- [ ] 不要なコメントアウト
- [ ] 設計書との乖離確認(docs/ の設計書・アーキテクチャ図など)

## PRの種類

- [ ] 機能開発
- [ ] 仕様変更
- [ ] バグ修正
- [ ] リファクタリング
- [ ] その他

## TODO
```

### 5. PRの作成

```bash
# 現在のブランチをプッシュ（未プッシュの場合）
git push -u origin HEAD

# PRを作成（オプションを条件に応じて組み合わせる）
gh pr create --base main \
  --title "PRタイトル" \
  [--draft] \           # --draft フラグが指定された場合
  --body "$(cat <<'EOF'
[上記で作成したPR本文]
EOF
)"
```

オプションの判定:
- `--draft`: 引数に `--draft` が含まれている場合に付与

### 6. 結果の報告

PRが作成されたら、以下の情報をユーザーに報告する:
- PR URL
- PRタイトル
- ベースブランチ（main）
- ドラフトPRかどうか

## 注意事項

- PRタイトルは変更内容を簡潔に表現してください（日本語可）
- コミットメッセージに `#123` などのIssue番号があれば、PR本文に含めてください
- 破壊的変更がある場合は、PR本文で明確に説明してください
- 大きな変更の場合は、概要で特にレビューしてほしいポイントを具体的に記載してください
- Mermaid図表のコンポーネント名・メソッド名は実際のコードと一致させること（架空の名前を使わない）
