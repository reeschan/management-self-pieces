# PBI-008: 取り込み結果を DB に反映する

- 担当モデル: opus (select_model.py: sensitive; scores {'novelty': 0, 'coupling': 1, 'ambiguity': 0})
- 依存: PBI-004, PBI-007

## 目的
PBI-007 の `ImportResult` を DB (`nodes` / `relations` / `import_errors`) に反映する。取り込んだリポジトリの範囲 (`scannedRepos`) の中だけを書き換え、範囲外の Node には触らない。何をどう変えるかの計算 (計画) は純粋関数にしてテストで確かめ、DB への書き込みは計画を実行するだけにする。

## 対象

### plan.ts
```ts
export type ExistingNode = { id: string; sourceRepo: string; sourceSha: string };
export type SyncPlan = {
  upserts: NewNodeRow[];                        // src/db/schema.ts の nodes の Insert 型
  relations: { fromId: string; toId: string; type: string }[]; // upserts の Node の関係 (全件)
  deleteIds: string[];                          // 消す Node の id
  errors: ImportError[];
  scopeRepos: string[];                         // 書き換える範囲
};
export function planSync(existing: ExistingNode[], result: ImportResult): SyncPlan;
```
- `scopeRepos` は `result.scannedRepos` をそのまま使う
- `upserts`: `result.manifests` すべて。manifest の項目を nodes の列に写す (`detail` → `detailPath`、`repo` → `sourceRepo`、`sha` → `sourceSha`、`updatedAt` は `new Date()`)
- `relations`: upserts の各 manifest の `relations` を `{ fromId: manifest.id, toId: r.to, type: r.type }` にする。同じ組は 1 件にまとめる
- `deleteIds`: `existing` のうち `sourceRepo` が `scopeRepos` に含まれ、かつ `result.manifests` に同じ id が無いもの
- 既存の Node と id が同じで `sourceRepo` が違う manifest (別リポジトリに移った) は、そのまま upsert する (sourceRepo が書き換わる)
- `errors`: `result.errors` そのまま

### apply.ts
`applySync(db: Db, plan: SyncPlan): Promise<void>`
- neon-http はトランザクションが使えないので `db.batch([...])` で 1 回にまとめる。順序:
  1. `deleteIds` の nodes を削除 (relations・external_refs は FK の cascade で消える)
  2. upserts を `insert ... onConflictDoUpdate` (target は `nodes.id`、更新するのは id 以外の全列)
  3. upserts の id を from に持つ relations を削除してから、plan.relations を insert
  4. `scopeRepos` と plan.errors に出るリポジトリ (重複を除いた和集合) の import_errors を削除してから、plan.errors を insert (同じエラーがたまり続けないように)
- 空の配列で insert しない (Drizzle は空配列の values で例外になる)。`batch` に入れる文が 0 件なら何もしない

### run.ts
- `runFullImport(): Promise<SyncSummary>`: `createRepoSource()` → `importAll` → DB から既存 Node (`id, sourceRepo, sourceSha`) を読む → `planSync` → `applySync`
- `runRepoImport(fullName: string): Promise<SyncSummary>`: 1 リポジトリ版 (`importRepo`)
- `applyImportResult(db: Db, result: ImportResult): Promise<SyncSummary>`: 既存の読み込み・計画・反映をまとめた関数。上の 2 つと PBI-012 の seed から使う
- `SyncSummary = { upserted: number; deleted: number; errors: number; scannedRepos: number }`

### cacheComponents についての共通の注意 (PBI-003 の結果から追記)
この repo の `next.config.ts` は `cacheComponents: true` (create-next-app の既定)。次を守る。詳細は `node_modules/next/dist/docs/01-app/02-guides/migrating-to-cache-components.md` と `authentication-with-cache-components.md`。
- route segment config の `export const dynamic = ...` は使えない (build エラーになる)。`export const runtime = "nodejs"` も書かない (既定が nodejs)。`maxDuration` は build が通れば残してよい
- Route Handler は、`request` の本文やヘッダーを読めば自動でリクエスト時に動く
- page / layout で `headers()`・`cookies()`・`searchParams`・セッションを読むときは、その部分を `<Suspense>` の中のコンポーネントに置くか、その page / layout に `export const instant = false` を付ける (ガイドの「Migrating an existing app」)。どちらにしたかを報告に書く
- 事前生成される部分で `new Date()`・`Date.now()`・`Math.random()` を呼ばない
