# PBI-019: API と Server Actions でも許可リストを確かめる

- 担当モデル: opus (select_model.py: sensitive)
- 依存: PBI-011, PBI-014

## 目的
許可リスト (`ALLOWED_EMAILS`) の判定は、ユーザー作成時 (PBI-005) と、ログイン必須の layout (PBI-006) で行っている。しかし API (`/api/nodes/[id]`・`/api/nodes/[id]/asset`) と Server Actions (`src/app/(app)/actions.ts`) は**セッションの有無しか見ていない**ため、許可リストから外したユーザーが既存のセッションでこれらを直接呼べてしまう。「許可リストに含まれるセッションだけを返す」共通の関数を作り、すべての入口で使う。

## 対象
- 変更 `src/lib/auth/server.ts`: `getAllowedSession()` を追加して export する。`getSession()` の結果が null、または `isAllowedEmail(session.user.email, authEnv().allowedEmails)` が false なら null を、それ以外はセッションを返す。既存の `getSession()` はそのまま残す
- 変更 `src/app/(app)/actions.ts`: 3 つの関数のセッション確認を `getAllowedSession()` に置き換える (null なら従来どおり `Error("unauthorized")`)
- 変更 `src/app/api/nodes/[id]/route.ts`、`src/app/api/nodes/[id]/asset/route.ts`: セッション確認を `getAllowedSession()` に置き換える (null なら従来どおり 401)

## 触らない範囲
- `src/app/(app)/layout.tsx`、`src/app/login/page.tsx` (すでに許可リストを確認している。ログイン画面は許可リスト外のセッションを見分ける必要があるので `getSession()` のまま)
- `src/lib/auth/allowlist.ts`、`src/lib/env.ts`、`src/db/`、`package.json`
- 上の 3 ファイルの、セッション確認以外の処理

## 受け入れ条件
1. 検証コマンド 1 の出力が `3` (actions.ts の 3 関数が getAllowedSession を使う)
2. 検証コマンド 2 の出力が `2` (2 つの API route が getAllowedSession を使う)
3. 検証コマンド 3 の出力が空 (actions.ts と API route に `getSession()` の直接呼び出しが残っていない)
4. 検証コマンド 4 が終了コード 0
5. 検証コマンド 5 が終了コード 0

## 検証コマンド
1. `grep -c "getAllowedSession()" "src/app/(app)/actions.ts"`
2. `grep -l "getAllowedSession()" "src/app/api/nodes/[id]/route.ts" "src/app/api/nodes/[id]/asset/route.ts" | wc -l`
3. `grep -n "getSession()" "src/app/(app)/actions.ts" "src/app/api/nodes/[id]/route.ts" "src/app/api/nodes/[id]/asset/route.ts"`
4. `pnpm typecheck`
5. `pnpm build`

## 補足
- `getAllowedSession()` は `getSession()` を呼んでから `authEnv()` を読む順にする (セッションが無いときに環境変数を読まない)
