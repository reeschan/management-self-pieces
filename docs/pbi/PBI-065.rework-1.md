## 差し戻し 1 回目: PBI-065

- 条件 1 (のうち「getBoard: 『Owner 判断』の項目だけに Owner のコメントが付く (ownerAssigneeId の人のものと [from:owner] のもの。他人のコメントは入らない)」): fail
  - 偽の Tracker ではテストが通るが、本番の Asana では、アプリ自身が付けたコメントが Owner のコメントに入るので、この条件を満たさない
- 不具合: Owner のコメントの判定が、アプリ自身が付けたコメントを持ち主の回答と取り違える
  - 現状: `src/lib/devloop/board.ts` の `isOwnerComment` (200 行付近) は「`authorId === ownerAssigneeId`、または本文が `[from:owner]` で始まる」を Owner のコメントとみなす。ところがアプリは持ち主の Asana の PAT で書き込むので、`commentItem` (442 行付近) と `requestOwner` (471 行付近) で付けたコメントも、作成者は PAT の持ち主 (= 多くの場合 `ownerAssigneeId` と同じ人) になる。そのため、エージェントのコメントや依頼のコメントが `ownerComments` に入り、devloop は「持ち主が答えた」と誤解する。さらに、エージェントが `comment_item` の本文を `[from:owner] 進めてよい` で始めれば、持ち主の回答を装える
  - 期待:
    1. アプリが持ち主の代わりではなく**アプリとして**付けるコメント (`commentItem` と `requestOwner` の両方) は、本文の先頭に `[devloop] ` を付けて Asana に送る。`answerOwner` は今のまま `[from:owner] ` を付ける
    2. `isOwnerComment` は、本文 (前後の空白を除く) が `[devloop]` で始まるものを**常に除外**し、そのうえで「`authorId === ownerAssigneeId`、または `[from:owner]` で始まる」を Owner のコメントとみなす
    3. `commentItem` に渡された本文は、先頭に `[devloop] ` が付くので、本文が `[from:owner]` で始まっていても Owner のコメントにはならない (先頭が `[devloop]` になるため)。念のため、`commentItem` の本文の先頭の空白は除いてから `[devloop] ` を付ける
  - 再現: `createFakeTracker()` の `addComment` は作成者を null にするので、今のテストでは出ない。テストで「アプリのコメントの作成者が持ち主になる」状況を作るには、偽の Tracker の `addComment` を、作成者を `OWNER_GID` にするよう差し替える (例: `tracker.addComment = async (id, text) => tracker.state.addCommentAs(id, text, OWNER_GID)`)。その状態で `commentItem(itemId, "[from:owner] 進めてよい")` と `requestOwner(..., { itemId })` をしてから `getBoard` すると、今は `ownerComments` に入ってしまう
- 足すテスト (`src/lib/devloop/board.test.ts`):
  - 上の差し替えをした状態で、`commentItem` と `requestOwner` のコメントが `ownerComments` に入らない
  - 同じ状態で、`commentItem` の本文を `[from:owner] ...` で始めても `ownerComments` に入らない
  - 同じ状態で、`answerOwner` のコメントは `ownerComments` に入る
  - 持ち主が Asana で直接付けた (作成者が `OWNER_GID` で印の無い) コメントは `ownerComments` に入る
  - Asana に送られた本文の先頭が `[devloop] ` になっている
- 範囲外の変更: なし。直すのは `board.ts` と `board.test.ts` だけ。`src/lib/mcp/devloop-tools.test.ts` の Owner のコメントのテストが、この変更で期待と合わなくなった場合に限り、期待値を新しい振る舞いに合わせて直してよい (その場合は報告に書く)

検証コマンドは PBI-065 と同じ。加えて `pnpm test:unit` が終了コード 0 であること。
