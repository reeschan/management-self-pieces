# PBI-068: MCP の口に看板のツールを足す (board 権限) と、get_board の置き換え

- 担当モデル: agent opus（opus 相当） (select_model.py: 決定: opus。sensitive; scores {'novelty': 0, 'coupling': 2, 'ambiguity': 0}。route 先頭の agy は使用不可のため agent)
- 依存: PBI-065, PBI-066, PBI-067

## 目的
devloop の PC 側のスキルが呼ぶ看板のツールを、M1 で作ったツールの共通の包み (`defineTool`: 権限・書き込みの回数・監査ログ・エラーの形) に乗せて足す。read の `get_board` も、看板のサービスを使う形に置き換える。

## 対象
- 変更 `src/lib/mcp/tools.ts`
  - `ToolContext` に `devloop: () => DevloopServices` を足す。`DevloopServices = { board: BoardService; control: ControlService }`。呼ばれたときに作る (Asana の環境変数が無ければ、その時点で例外 → ツールは `internal_error`)
  - `defineTool`・`UNTRUSTED_NOTE`・`requireNode` を export する (別ファイルから使うため)
  - `get_board` を、`ctx.devloop().board.getBoard(node_id, { sections })` を返す形に置き換える。`sections` は `SECTIONS` の値だけを受け付ける。description を看板の説明に直す (末尾の `UNTRUSTED_NOTE` は残す)
  - `registerTools` の最後で `registerBoardTools(server, ctx)` を呼ぶ
  - 例外の変換: `BoardLimitError` は `ToolError(code, message)`、`BoardError` は `ToolError(code, message)` として返す。`defineTool` の中か、各ツールの中のどちらで変換してもよい
- 新規 `src/lib/mcp/devloop-tools.ts`: `registerBoardTools(server, ctx)`。すべて `scope: "board"`、`write: true`
  - `create_item`: 入力 `{ node_id, section: "Inbox" | "Backlog", name (1〜200), notes (0〜10,000), type (ITEM_TYPES), origin: "pm" | "biz" | "tl", meta? }`。出力 `{ id }`
  - `move_item`: 入力 `{ node_id, item_id (1〜40), section (SECTIONS) }`。Sprint の上限は `control.getSettings(node_id).sprintLimit`
  - `update_item`: 入力 `{ item_id, node_id?, meta }` (meta は丸ごと置き換え)
  - `comment_item`: 入力 `{ item_id, node_id?, text (1〜5,000) }`
  - `request_owner`: 入力 `{ node_id, title (1〜200), reason (1〜5,000), item_id? }`
  - meta の入力は `ItemMetaSchema` で検証する。description は、仕様の M2 のツールの説明に沿って短く書き、末尾に `UNTRUSTED_NOTE` を付ける
- 変更 `src/lib/mcp/handler.ts`: `McpDeps` に `tracker: () => TrackerProvider` と `ownerAssigneeId: string | null` を足す。`ToolContext.devloop` は、この 2 つと `db`・`now` から、1 リクエストにつき 1 回だけ作る
- 変更 `src/app/api/mcp/route.ts`: `tracker: () => getTracker()` (`@/lib/tracker/service`)、`ownerAssigneeId: asanaOwnerGid()` を渡す
- 変更 `src/lib/env.ts`: `asanaOwnerGid(source = process.env): string | null` を足す (`ASANA_OWNER_GID`。未設定か空なら null。例外を投げない)。`.env.example` に `ASANA_OWNER_GID=` を説明付きで足す
- 変更 `src/lib/mcp/handler.test.ts`: `McpDeps` の変更に合わせて、偽の Tracker を渡す (既存のテストの中身は変えない)。`get_board` のテストは新しい形に合わせて直す
- 新規 `src/lib/mcp/devloop-tools.test.ts`: `handleMcpRequest` に JSON-RPC を送る形で、`createTestDb()` と `createFakeTracker()` を使う

## 触らない範囲
- `gate.ts`・`tokens.ts`・`ip*.ts`・`rate-limit.ts`・`audit.ts`
- `src/lib/devloop/` のサービス (使うだけ)
- `list_nodes`・`get_project` (get_project は PBI-069 で直す)

## 受け入れ条件
1. 検証コマンド 1 が終了コード 0。少なくとも次を確かめる
   - read だけのトークンで `create_item` を呼ぶと `forbidden:`
   - `create_item`: Inbox に作れて id が返る。section に Sprint や「Owner 判断」を渡すと入力エラー。origin に owner を渡すと入力エラー。Inbox が 15 件だと `inbox_full:`
   - `move_item` の Sprint の上限 (Node の sprintLimit を使う) で `sprint_full:`
   - `update_item` / `comment_item`: 別の Node の項目に node_id を付けて呼ぶと `node_mismatch:`。写しにも無い項目は `not_found:`
   - `request_owner` で「Owner 判断」に項目ができる
   - `get_board` が列ごとの形で返り、「Owner 判断」の項目に Owner のコメントが付く
   - 書き込みのツールの成功で、監査ログに `ok` が残る。ホストでは書き込みの回数が数えられる
   - Asana がつながっていない Node で `not_linked:`
2. 検証コマンド 2 が終了コード 0 (M1 のテストも通る)
3. 検証コマンド 3 が終了コード 0
4. 検証コマンド 4 が終了コード 0
5. 検証コマンド 5 が終了コード 0

## 補足
- 復元した `R/lib/devloop/mcp-tools.ts` がツールの元の形 (入出力の名前はこれに合わせる)。ただし、権限・監査・回数は M1 の `defineTool` に任せ、R の自前の `defineTool` は使わない
- ルートでは、環境変数をモジュールの読み込み時に読まない
